Mobius coding style

Before any engine code is written, we fix how it will look and how it will be organised. Your answers here become docs/coding-style.md, an .editorconfig and possibly a .clang-format file. Every card has a recommendation already selected, so you can change only the ones you disagree with.

20 decisions4 sections~25 minutes
Already decided

Fixed choices, not up for a vote

  • Compiler. MSVC only (Visual Studio 2026, toolset 14.52 or newer), built with /std:c++latest. C++23 is the guaranteed baseline, and a separate /std:c++23 build must also pass. Newer language features only appear behind feature-test macros.
  • Tools. Sharpmake builds the project, doctest runs the tests, simdjson parses JSON and we write our own JSON writer.
  • Folders. engine/core/{math, mesh, analysis, symmetry, guidance, backend, pipeline, io, eval}, plus engine/core/ops/retopo, engine/capi, engine/cli, tests/unit and tests/regression. The root namespace is mobius.
  • Mesh data. Meshes use structure-of-arrays storage with uint32_t indices. Maths types (Vec<T,N>, Mat<T,R,C>, Frame) are plain value types.
  • Public C API. A C99 header with a mobius_ prefix, snake_case functions, opaque handles such as mobius_mesh* and status-code returns. The Blender addon calls it through ctypes. Example: mobius_status mobius_mesh_load(const char* path, mobius_mesh** out);
1 · Naming

Names of things

These choices decide how every line of Mobius reads. They are cheap to set now and expensive to change later.

Decision 01 of 20

How should classes, structs, enums and aliases be spelled?

Type names. Types are the nouns of the code. A clear spelling lets you tell a type from a variable at a glance, for example Frame versus frame.

Recommendation: PascalCase keeps types visually separate from functions and variables. Math code often wants a variable named after its type, and PascalCase makes that legal and readable.

Decision 02 of 20

How should functions, methods, local variables and parameters be spelled?

Function and variable names. Most of the code you read is functions and variables. This choice also decides whether the C++ code and the C API look related.

Recommendation: snake_case matches the standard library, which your code calls constantly, and it matches the fixed C API names. The Blender addon in Python also uses snake_case.

Decision 03 of 20

How should private member variables of a class be marked?

Private data members. Inside a method you want to see at once whether a name is a local variable or part of the object. It also avoids clashes between constructor parameters and members.

Recommendation: A trailing underscore is short and clear. It also lets a struct with public members (no underscore) and a class with private members be told apart in any code snippet.

Decision 04 of 20

How should constants and enum values be spelled?

Constants and enumerators. Constants appear in solver settings and enum options all over the pipeline. Some spellings clash with macros that Windows headers define, which causes confusing compile errors.

Recommendation: PascalCase is short, avoids macro clashes, and the qualified enum name already tells you what it is. Macros are always MOBIUS_UPPER_CASE (fixed), so a constant and a macro can never be confused.

Note. Fixed: macros are always MOBIUS_UPPER_CASE, for example MOBIUS_ASSERT and MOBIUS_API.

Decision 05 of 20

How should source files be named, and which extension do C++ headers use?

File names and extensions. File names show up in every include line, in Sharpmake, in test paths and in the Blender addon docs. The C API header stays mobius.h (C99) whatever you pick here.

Recommendation: snake_case files match the function and namespace style, avoid case problems across systems, and .hpp keeps the C header (.h) clearly separate.

2 · Layout and formatting

How the code looks on the page

Formatting is the part a tool can do for you. Decide it once so nobody ever argues about it again.

Decision 06 of 20

Should a tool format the code automatically, or do we format by hand following the rules?

Automatic formatting. Automatic formatting removes style noise from reviews and keeps AI-written and hand-written code identical. clang-format ships with Visual Studio. It only formats text and does not compile anything, so it does not conflict with the MSVC-only rule. It is still a new tool in the project, so you need to approve it.

Recommendation: Because Mobius code will be written in many sessions, a tool keeps it consistent for free. A .editorconfig is added in both cases. Please confirm explicitly that you approve clang-format.

Note. Exact menu names can differ between Visual Studio versions. If format on save is not offered for C++ in yours, the fallback is formatting with Ctrl+K, Ctrl+D or a script in tools/, with the same .clang-format file.

Decision 07 of 20

Where does the opening brace go?

Brace style. Math-heavy code has many short blocks. The brace style decides how much of a function fits on the screen. Indent is 4 spaces in both options.

Recommendation: Compact code lets you see a whole algorithm at once. clang-format can do K&R with one setting, so it costs nothing to keep.

Decision 08 of 20

How many characters may a line have before it is wrapped?

Maximum line length. Long lines make diffs and side-by-side windows hard to read. Maths expressions and template signatures are the lines that push the limit.

Recommendation: 100 is the usual middle ground for modern C++. It is also what the .clang-format sample uses.

Decision 09 of 20

Where do const and the * or & go in a declaration?

const and pointer placement. Every function parameter is affected, so this is in almost every line of the public headers.

Recommendation: West const is what most C++ you will read, and most code AI tools write, looks like. The star and ampersand stay with the type in both options.

Decision 10 of 20

In what order are #include lines written?

Include order. A fixed order exposes missing includes. When a file includes its own header first, that header is proven to work on its own.

Recommendation: The own-header-first rule is recommended by the Core Guidelines and quietly finds a whole class of bugs. clang-format can sort this for you.

3 · Language usage

How we use C++ itself

These choices affect correctness more than looks. They decide which mistakes the compiler can catch for us.

Decision 11 of 20

Should a vertex index, a face index and an edge index be different types?

Strong index types. A mesh is many arrays addressed by integers. Mixing up a vertex index with a face index compiles fine with plain integers and produces wrong geometry that is very hard to find.

Recommendation: Retopology code constantly walks from vertices to faces to edges, which is exactly where this bug lives. The wrapper costs nothing at run time.

Decision 12 of 20

Which number type should geometry and solvers use inside the engine?

Scalar precision. Curvature, cross-field and quad extraction solves are sensitive to rounding. Blender stores float, so there is a conversion at the boundary either way.

Recommendation: A single scalar type keeps the code simple and numerically safe. Performance can be revisited later if memory ever becomes the problem.

Decision 13 of 20

When may you write auto instead of the full type?

Use of auto. auto saves typing and is required for lambdas, but it can hide what a variable is. This rule decides how much a reader has to guess.

Recommendation: The middle rule is the one the Core Guidelines lean towards. It keeps numeric types visible, where mistakes are most costly.

Decision 14 of 20

Do you confirm the error model already designed in D10?

Error handling confirmation (D10). This decides what every function that can fail looks like. The C API cannot let a C++ exception cross the DLL boundary, so it needs status codes anyway.

Recommendation: It is the design already in D10. std::expected is in C++23, which is our guaranteed baseline.

Decision 15 of 20

Which functions should be marked [[nodiscard]]?

Use of [[nodiscard]]. If a function returns an error or a computed result, ignoring it is almost always a bug. [[nodiscard]] makes the compiler warn about that.

Recommendation: With errors as return values, an ignored return is an ignored failure. The rule is simple: if it returns something useful, mark it.

Decision 16 of 20

When should a type be a struct and when a class?

Classes and structs. This decides which data is open for anyone to change and which is protected by member functions.

Recommendation: It is the Core Guidelines rule (C.2): use struct when members can vary independently, and class when there is an invariant.

4 · Structure, comments and tests

How the project is organised

These choices shape the folders, the build and what a new reader sees first.

Decision 17 of 20

Should we organise code with header files, or with C++20 named modules?

Headers or C++20 named modules. This is the biggest structural choice. Modules can build faster and give cleaner boundaries, but they are the newest part of the language and the tools around them matter.

Recommendation: Headers are the safe, well-supported default and a later switch is possible. This is only a recommendation until modules are verified on this toolchain.

Note. Modules need verification before anyone relies on them: check MSVC module support, IntelliSense, clang-format and Sharpmake handling in a small test project. Nothing here says it works or fails.

Decision 18 of 20

How are namespaces arranged?

Namespaces. Namespaces keep names short inside a module and prevent clashes. They also show where each piece of code belongs.

Recommendation: It mirrors the folder layout you already decided, so a reader can guess where code lives from its name.

Decision 19 of 20

How much commenting is expected, and in what style?

Comments and API documentation. Comments are how a non-expert reader, and tomorrow's session, learns what a function promises. The wrong kind goes stale quickly.

Recommendation: A short brief on each public function is what lets an owner who is not a domain expert follow the headers. The "why" rule keeps implementation comments useful.

Decision 20 of 20

How are the doctest tests organised and named?

Test layout and naming. When a test fails you want to find its source file immediately, and the failure message should say what was expected.

Recommendation: A mirrored layout makes it obvious what is tested and what is missing. The test name carries the expected result, which matters for the regression suite.
