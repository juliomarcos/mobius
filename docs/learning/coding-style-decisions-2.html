Part 1 fixed how the code looks. This page fixes how it is designed: who owns data, how errors and checks work, how loops and functions are shaped and how the code is tested. Every concept is explained first, in plain words, before the question. Every card has a recommendation already selected, so you can change only the ones you disagree with.

The ideas behind this page

Most questions come from five ideas. Each card below is short. The first four are the main line of thought, and the fifth is the answer from the other side.

Parent's three goals

Sean Parent's talk C++ Seasoning gives three goals for better code. First, no raw loops: a loop that does more than one named job should become a standard algorithm or a named function. Second, no raw synchronization primitives: mutexes, atomics, semaphores and memory fences are for library builders, not for everyday code. Third, no raw pointers: a pointer that stands for ownership and shared access is hard to reason about.

S1 Parent, C++ Seasoning (slides)

Value semantics and local reasoning

A variable owns its value, and a copy is independent of the original. Then you can understand a function by reading only that function, without knowing the rest of the program. Parent, Abrahams and Lakos each describe this idea from a different side. It is the base of decisions 01, 03 and 10 to 12.

S3 Parent, Value Semantics and Concept-based Polymorphism (slides) · S9 Parent, Local Reasoning in C++ (slides) · S11 Abrahams, Value Semantics · S14 Lakos, Value Semantics

Regular types

Stepanov and McJones call a type regular when it behaves like the built-in types. You can create one, copy it, assign it and compare it, and the parts fit together with the standard algorithms and containers. Decision 02 applies this to equality.

S12 Stepanov and McJones, Elements of Programming · S13 Dehnert and Stepanov, Fundamentals of Generic Programming

Contracts

A contract says what a function needs from its caller (the precondition), what it gives back (the postcondition) and what stays true of an object (the invariant). A narrow contract trusts the caller. A wide contract checks everything and reports errors. C++26 adds contracts to the language, but MSVC does not have them yet.

S8 Parent and Abrahams, Better Code: Contracts (slides) · S15 Lakos, Defensive Programming Done Right · S24 P2900 Contracts for C++

The counterweight: data-oriented design

Mike Acton's view is that a program exists to transform data, so you should know your data and the machine it runs on. Abstraction layers have costs, and Mobius processes meshes of 500k vertices, so the costs show. Parent and Acton agree on two points: both dislike deep inheritance hierarchies and both dislike hidden shared state. They pull apart on style. Parent favours named abstractions and algorithms, while Acton favours explicit loops over plain arrays.

S16 Acton, Data-Oriented Design and C++ · S17 Fabian, Data-Oriented Design · S18 Muratori, Clean Code, Horrible Performance

1 · Values and types

What a value is, and what it costs to copy

These choices decide whether data in Mobius behaves like plain numbers or like shared objects. Everything else on this page builds on them.

Decision 01 of 22

Should Mobius types behave like values, or like shared objects?

The idea

A value is an object that a variable owns outright. With value semantics, a copy is a separate object, so changing the copy never changes the original. The built-in int works this way. With reference semantics, several names reach one object (pointers, references stored inside objects, std::shared_ptr), so a change through one name shows up through all the others. Then you must know the whole program to know what one line does. Parent and Abrahams argue that values let you understand a function by reading only that function, which is called local reasoning. Mobius needs repeatable results, so this choice sets how safe sharing data between stages will be.

Recommendation: Option A. A stage cannot change data that another stage holds, which keeps runs repeatable and each function readable on its own. Main trade-off: you must think about the cost of copying big data, which decision 03 handles.

Sources: S3 Parent, Value Semantics and Concept-based Polymorphism (slides) · S11 Abrahams, Value Semantics · S14 Lakos, Value Semantics · S9 Parent, Local Reasoning in C++ (slides) · Core Guidelines C.11

Decision 02 of 22

What should == mean for Mobius value types, and which types are regular?

The idea

Stepanov called a type regular when it behaves like int: you can default-construct it, copy it, assign it and compare it with ==, and a copy equals the original. C++20 names this as the concept std::regular. For floating-point data there are two separate questions: are these exactly equal, and are these close enough. Close enough is not a true equality, because a close to b and b close to c does not make a close to c, so it should not be spelled ==. Mobius promises bit-identical results, so its tests need exact comparisons. Exact == on doubles treats 0.0 and -0.0 as equal and NaN as unequal to itself, so bit-identity tests compare the raw bytes instead.

Recommendation: Option A. One meaning for == lets containers, algorithms and tests work, and determinism tests can compare directly. Main trade-off: exact == on doubles surprises beginners (0.1 + 0.2 is not 0.3), so tests on computed values must call approx_equal on purpose.

Sources: S13 Dehnert and Stepanov, Fundamentals of Generic Programming · S12 Stepanov and McJones, Elements of Programming · Core Guidelines C.11

Decision 03 of 22

How should a very large object such as the working mesh be copied?

The idea

A 500k-vertex working mesh is tens of megabytes. With almost-always auto (already decided), auto mesh = context.mesh; silently copies it, while const auto& mesh = context.mesh; does not. Moving an object transfers its contents to a new owner without copying them. A type that copies, assigns and compares like int is fully regular. There are three choices: keep heavy types copyable, make them move-only with an explicit clone() for a deliberate copy, or share one immutable buffer and copy it only on the first write (copy-on-write).

Recommendation: Option B. Under almost-always auto an accidental 50 MB copy compiles without a sound. With B it is a compile error and the fix, clone(), is visible. Main trade-off: those few types are not std::regular, so they cannot go into containers that require copying (equality can still be defined). C keeps full regularity but hides a reference count.

Sources: S4 Parent, Better Code: Data Structures · S3 Parent, Value Semantics and Concept-based Polymorphism (slides) · S14 Lakos, Value Semantics · Core Guidelines F.16

Decision 04 of 22

How strictly should Mobius use const?

The idea

An object that never changes after it is made is easy to reason about. const on a local variable says that this name will not change for the rest of the function. A function that only reads its input takes it by value or as a const&, which is a read-only reference. A const member function promises not to change the object.

Recommendation: Option A. A reader sees at once which names change, and the compiler enforces it. Main trade-off: more const words, and the return-value exception must be remembered.

Sources: Core Guidelines Con.1 · Core Guidelines Con.4

2 · Polymorphism and generic code

Choosing behaviour at run time and writing code for many types

Two ways to avoid writing the same code twice, each with a price. The page explains both before it asks.

Decision 05 of 22

How should Mobius pick behaviour at run time, for example a strategy chosen by name?

The idea

Runtime polymorphism means choosing behaviour while the program runs, for example picking the field strategy by its registered name (design D9). A virtual base class uses inheritance: callers hold a pointer to the base. Type erasure, Parent's concept-based polymorphism, is a value type that can hold any type with the right functions, as std::function does for callables, with the virtual calls hidden inside. std::variant holds one of a closed list of types that is known when compiling, and std::visit handles each case. Templates choose at compile time. Parent argues that inheritance forces reference semantics, meaning heap objects behind pointers, on every user of a type. Muratori shows that a virtual call per element, or many tiny polymorphic objects, costs real speed. This decision sets how the stage interfaces of D9 are spelled.

Recommendation: Option A. Strategies stay values (copyable settings, comparable, no pointer handling at the call site), and closed sets get compiler-checked exhaustive handling. Main trade-off: a type-erased wrapper is about 30 lines of boilerplate per interface and is less familiar than a base class. B is simpler to write and read.

Sources: S2 Parent, Inheritance Is The Base Class of Evil · S3 Parent, Value Semantics and Concept-based Polymorphism (slides) · S6 Parent, Better Code: Runtime Polymorphism · S18 Muratori, Clean Code, Horrible Performance · Core Guidelines C.120 · Core Guidelines C.67

Decision 06 of 22

When may code be written as a template?

The idea

Generic programming, Stepanov's idea, writes an algorithm once for every type that meets stated requirements. A template is the C++ tool for this. A concept names the requirements, so a wrong type gives a short error message instead of a long one. The costs are longer compile times, harder error messages and code that is harder for a newcomer to read.

Recommendation: Option A. Mobius has one mesh type, so generic algorithms would add cost without a second user, and concepts keep the few templates readable. Main trade-off: if a second mesh type appears later, some algorithms must be made generic then.

Sources: S12 Stepanov and McJones, Elements of Programming · Core Guidelines T.10

3 · Algorithms, functions and interfaces

How loops, functions and their arguments look

These choices shape almost every function you will read in the engine.

Decision 07 of 22

When may a plain loop appear in the code?

The idea

Parent's rule paraphrased: a raw loop is a loop inside a function whose purpose is larger than the algorithm the loop implements. The cure is a standard algorithm (std::ranges::transform, std::ranges::count_if and others), or moving the loop into its own well-named function. The counterweight is that a plain loop over an array is clear, easy to debug and easy to make fast. Range views, which are lazy pipelines joined with |, add layers that are not inlined in Debug builds, so Debug runs can be slower.

Before: one loop doing four jobs
auto process(const working_mesh& mesh) -> double {
    auto areas = std::vector<double>{};
    auto total = 0.0;
    for (auto i = std::uint32_t{0}; i < mesh.face_count(); ++i) {
        const auto a = face_area(mesh, face_index{i});
        areas.push_back(a);
        total += a;
        if (a < 1e-12) {
            log_degenerate(i);
        }
    }
    return total;
}
After: each step has a name
[[nodiscard]] auto face_areas(const working_mesh& mesh) -> std::vector<double> {
    auto areas = std::vector<double>(mesh.face_count());
    std::ranges::transform(mesh.faces(), areas.begin(),
                           [&](face_index f) { return face_area(mesh, f); });
    return areas;
}

[[nodiscard]] auto total_area(std::span<const double> areas) -> double {
    return std::ranges::fold_left(areas, 0.0, std::plus{});
}

// The caller composes the named steps:
const auto areas = face_areas(mesh);
report_degenerate_faces(areas);
const auto total = total_area(areas);

Recommendation: Option A. Every loop gets a name that says what it does, and well-known algorithms are not rewritten by hand. Main trade-off: more small functions. Numerical sweeps such as a Gauss-Seidel pass stay loops but live in their own named function.

Sources: S1 Parent, C++ Seasoning (slides) · Core Guidelines ES.1 · Core Guidelines ES.3 · Core Guidelines ES.71 · S16 Acton, Data-Oriented Design and C++

Decision 08 of 22

Should algorithms be member functions of the mesh, or free functions?

The idea

A member function can see a class's private data, so every member is one more place that can break the class's invariant. An invariant is a fact that must always be true of an object. Core Guideline C.4 and Meyers say: make a function a member only if it needs the private representation, and make everything else a free function. The standard library works this way: std::ranges::sort(v), not v.sort().

Recommendation: Option A. The mesh class stays small, so its invariants have few places to break, and algorithms live in the module they belong to. Main trade-off: dot-completion in the editor shows less. Typing mobius::analysis:: shows the algorithms instead.

Sources: Core Guidelines C.4 · S19 Meyers, How Non-Member Functions Improve Encapsulation · S12 Stepanov and McJones, Elements of Programming

Decision 09 of 22

How should functions take input and give output?

The idea

This decision covers how a function receives its inputs and hands back its results. The Core Guidelines say: pass cheap types by value and others by const&, return results instead of writing through output parameters, return a struct when there are several results, and keep the parameter count low. C++20 designated initializers let a call name its settings, for example smooth_field(mesh, angles, {.iterations = 20, .weight = 0.5}). A std::span is a view of a run of elements that someone else owns.

Recommendation: Option A. A call reads like a sentence and every result is visible at the call site. Main trade-off: designated initializers must follow declaration order or the code does not compile, and returning large values relies on moves, which are cheap.

Sources: Core Guidelines F.16 · Core Guidelines F.20 · Core Guidelines F.21 · Core Guidelines I.23

4 · Ownership, lifetimes and state

Who owns data, how long it lives and what is hidden

Many of the hardest C++ bugs come from unclear ownership. These rules make ownership visible in the code.

Decision 10 of 22

Who owns an object, and how is that written in the type?

The idea

The owner of an object is the one that destroys it. A raw owning pointer, such as T* p = new T, leaves it to human memory to free the object. That is what Parent's no raw pointers goal is about. std::unique_ptr is a single owner. std::shared_ptr has several owners. Parent's slide on shared pointers says: "A shared pointer is as good as a global variable" (S1). The reason is that anyone holding it can change the object.

Recommendation: Option A. Ownership is visible in the type, and there is no shared mutable state. Main trade-off: you must decide who owns what up front, and run results must own their outputs by moving them in.

Sources: S1 Parent, C++ Seasoning (slides) · Core Guidelines R.3 · Core Guidelines R.20 · Core Guidelines R.21 · Core Guidelines I.11 · Core Guidelines R.1

Decision 11 of 22

Where may a view (a span, a string_view, a reference) be stored?

The idea

A view such as std::span, std::string_view or a reference points into data that someone else owns. If the owner is destroyed, or a std::vector grows and moves its storage, the view dangles. Using a dangling view is undefined behaviour, which means the program may do anything. It is the worst kind of bug because it can seem to work for a while. Indices survive reallocation, which is one reason D3 uses strong indices.

Recommendation: Option A. Every dangling-view risk is named and searchable. Main trade-off: some convenience structs need an index plus the mesh passed separately.

Sources: S9 Parent, Local Reasoning in C++ (slides) · S11 Abrahams, Value Semantics · Core Guidelines R.3

Decision 12 of 22

May code use global or static variables that can change?

The idea

A global or static variable that can change is a hidden input to every function that reads it. It breaks local reasoning, because the function signature no longer shows everything the function depends on. It also breaks determinism, which means getting the same result on every run. A global random generator, or a global log written from several threads, gives different results from run to run.

Recommendation: Option A. Every input of a function is visible in its signature, which the determinism promise of D9 depends on. Main trade-off: some extra parameters, and a future profiler will need its own decision.

Sources: Core Guidelines I.2 · S9 Parent, Local Reasoning in C++ (slides) · design D9

5 · Contracts, invariants and errors

What a function promises, and what happens when a promise breaks

Mobius runs inside Blender, so a failure must never take Blender down with it.

Decision 13 of 22

Who checks that a function was called with valid input?

The idea

A contract is a function's promise. Preconditions are what the caller must make true, such as v is a valid vertex of mesh. Postconditions are what the function promises back. Invariants are what is always true of an object. A narrow contract assumes valid input, so a wrong call is a bug in the caller (std::vector::operator[]). A wide contract accepts any input and reports bad input as an error (std::vector::at). Lakos argues that making a naturally narrow contract artificially wide costs speed, hides bugs and bloats error handling. C++26 adds language contracts (pre, post, contract_assert), which MSVC does not implement yet, so a macro, MOBIUS_ASSERT, stands in.

Recommendation: Option A. User data is checked once, where errors are expected. Internal misuse is a bug and is caught loudly. Main trade-off: internal callers must respect the documented preconditions, so every brief must state them.

Sources: S15 Lakos, Defensive Programming Done Right · S8 Parent and Abrahams, Better Code: Contracts (slides) · S24 P2900 Contracts for C++ · Core Guidelines I.5 · Core Guidelines I.6 · Core Guidelines I.7

Decision 14 of 22

What happens when an internal check fails, and which checks run in Release builds?

The idea

Mobius runs as a DLL inside the artist's Blender. If the engine calls abort(), Blender closes and unsaved work is lost. D10 already says exceptions are for programmer errors and that the C API catches everything. Checks also differ in cost. The check index < count is nearly free, while validating a whole mesh is O(n), meaning its time grows with the mesh size, and is too slow to run after every edit in Release. Lakos uses several assert levels that are selected at build time.

Recommendation: Option A. Bugs are caught in Release too, and an artist never loses a Blender session to an engine bug. Main trade-off: after a violation the data of that run may be broken. That is safe only because the engine works on its own copies of the input (D11) and throws the whole run away. Cheap checks cost a little Release speed.

Sources: S15 Lakos, Defensive Programming Done Right · S10 Parent, All the Safeties · S8 Parent and Abrahams, Better Code: Contracts (slides) · design D10

Decision 15 of 22

What protects the half-edge mesh from becoming inconsistent?

The idea

In a half-edge mesh each edge is split into two half-edges that point in opposite directions. Each half-edge knows its next half-edge around the face, its twin on the other side, its origin vertex and its face. Invariants include: twin(twin(h)) == h, next(next(next(h))) == h on a triangle, the origin of twin(h) is the target of h, and boundary half-edges use a sentinel value. If any of these breaks, every algorithm silently computes garbage. D3 also needs edits, because feature curves are embedded by splitting triangles.

Recommendation: Option A. It is the same design as pmp-library and geometry-central, and the invariants get one guardian. Main trade-off: every new kind of edit must be written as an invariant-keeping operator.

Sources: Core Guidelines C.2 · S22 pmp-library tutorial · S23 geometry-central surface mesh navigation · reading list #2, Botsch et al., Polygon Mesh Processing

Decision 16 of 22

What does the error type hold, and how are non-fatal problems reported?

The idea

D10 already fixed that failures return std::expected<T, error>. Still open: what error holds, and how non-fatal problems are reported, such as the solver hitting its iteration cap, symmetry being weak, or a stroke being ignored. A warning is not an error. The run continues and the result is still valid.

Recommendation: Option A. There is one mapping to the C API, and warnings are part of a stage's result instead of hidden global state (decision 12). Main trade-off: the central error_code enum is touched by every module.

Sources: design D10, D11, D12 · Core Guidelines E.2 · Core Guidelines E.3 · S9 Parent, Local Reasoning in C++ (slides)

6 · Data layout and performance

How data sits in memory and when memory may be allocated

Mobius processes meshes of 500k vertices, so layout matters. Only the cheap rules are decided here.

Decision 17 of 22

How is data stored for each vertex, face or edge?

The idea

Array of structures (AoS) keeps all data of one vertex together: a std::vector<vertex_data> where vertex_data holds position, normal and curvature. Structure of arrays (SoA) keeps one array per attribute: one array of positions, one of normals, one of k1. A loop that needs only positions then reads only positions, which suits the CPU cache, GPU buffers (D9) and the C API's flat arrays. D3 already chose SoA for mesh connectivity. This decision covers everything else: analysis results, fields and guidance weights.

Recommendation: Option A. It is cache-friendly and GPU-ready without making maths code awkward. Main trade-off: data for one vertex is spread over several arrays, so debugging one vertex means looking in several places.

Sources: S16 Acton, Data-Oriented Design and C++ · S17 Fabian, Data-Oriented Design · Core Guidelines Per.19 · S22 pmp-library tutorial

Decision 18 of 22

May code allocate memory inside loops that run per element or per iteration?

The idea

Heap allocation (new, or a std::vector that grows) is slow compared with arithmetic, and it takes an unpredictable amount of time. Inside a loop over 500k vertices, or inside a solver's iterations, it can dominate the run time. A scratch buffer is a work array that is created once and reused.

Recommendation: Option A. It is the cheapest rule that avoids the most common performance trap, with no new machinery. Main trade-off: some functions get an extra scratch-buffer parameter.

Sources: S16 Acton, Data-Oriented Design and C++ · S18 Muratori, Clean Code, Horrible Performance · Core Guidelines Per.7

7 · Concurrency

Who may use threads

One decision, tied to the determinism promise: the same input gives the same bytes on any number of threads.

Decision 19 of 22

Which code may use threads, mutexes and atomics?

The idea

A data race is two threads touching the same memory at once, with at least one writing and no synchronization. It is undefined behaviour. Parent's goal of no raw synchronization primitives means that algorithm code should not use mutexes, atomics, semaphores or fences directly, but a higher-level tool such as tasks. D9 already fixes an in-house parallel_for with fixed chunk boundaries, so results are bit-identical for any thread count.

Recommendation: Option A. There are no data races by construction, and determinism is guaranteed in one place. Main trade-off: scattered writes (building adjacency lists) need a two-pass count-then-fill pattern instead of a lock, which is more code but deterministic.

Sources: S1 Parent, C++ Seasoning (slides) · S5 Parent, Better Code: Concurrency · Core Guidelines CP.2 · Core Guidelines CP.3 · Core Guidelines CP.4 · design D9

8 · Names of relationships

How mesh navigation and function names read

Names are the cheapest documentation. These two choices make them tell the reader more.

Decision 20 of 22

How does code walk from one half-edge to its neighbours?

The idea

Parent's Better Code: Relationships says that a relationship is a connection between objects, such as the twin or the next half-edge of this half-edge. Code should state relationships explicitly and keep them consistent. Mesh libraries spell this navigation in three ways: queries on the mesh that take index values, cursor handles that carry a pointer to the mesh, or direct access to the arrays.

Recommendation: Option A. It keeps indices as values (decisions 01 and 11) and keeps the arrays private (decision 15). Main trade-off: chains read inside-out, mesh.origin(mesh.twin(mesh.next(h))), so small helpers such as mesh.target(h) cover the common chains.

Sources: S7 Parent, Better Code: Relationships · S22 pmp-library tutorial · S23 geometry-central surface mesh navigation

Decision 21 of 22

Should a function name tell you if it changes data, and if it is cheap?

The idea

The Swift API guidelines name functions by their side effects. A function with no side effects reads as a noun (length(v), mesh.vertex_count()). One that changes something reads as an imperative verb (normalize(v), flip_edge(...)). A mutating and a non-mutating pair uses the verb and its past participle: normalize(v) changes v, while normalized(v) returns a new value, like sort and sorted. std::vector::empty() shows why this matters. It reads like a verb, but it only asks a question.

Recommendation: Option A. The name alone tells a reader whether a call changes data and whether it is cheap. Main trade-off: it needs judgment on what counts as cheap.

Sources: S20 Swift API Design Guidelines · Core Guidelines F.1

9 · Testing

Which kinds of tests exist

The last decision. It builds on the test layout already fixed in decision 003.

Decision 22 of 22

Which kinds of automated tests should the project have?

The idea

An example test checks one input against one expected output. A property-based test (QuickCheck) states a rule that must hold for all inputs and checks it on many generated inputs with a fixed seed, for example that after any sequence of edge flips check_invariants finds nothing and V - E + F is unchanged. A golden test compares output with a stored file byte for byte, which the deterministic JSON writer of D12 makes possible. A determinism test runs the same work on 1 and on 8 threads and requires identical bytes. Decision 003 already fixed the file layout (mirrored paths, SUBCASE).

Recommendation: Option A. Random inputs find the mesh edge cases nobody thinks of, and determinism is tested where it can break. Main trade-off: generators for valid random meshes take work to write.

Sources: S21 Claessen and Hughes, QuickCheck · design D9, D12, D13
